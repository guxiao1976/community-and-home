## 🎯 系统特性

### 核心设计原则

1. **智能体隔离**
   - 每个任务启动独立的开发智能体（worktree 隔离）
   - 避免代码冲突，支持并行开发

2. **智能体复用**
   - 同一任务的修复使用同一个开发智能体
   - 同一任务的重测使用同一个测试智能体
   - 保持上下文，提高修复效率

3. **路径传递**
   - 智能体之间只传递文件路径
   - 不传递大段文本内容
   - 减少 token 消耗，提高效率

4. **状态持久化**
   - 所有状态保存在 `task-status.json`
   - 支持中断恢复
   - 完整的审计追踪

5. **自动化修复**
   - 测试失败自动通知开发智能体
   - 最多重试 3 次
   - 智能迭代直到通过

## 📋 工作流程

### 完整流程

```
用户提供需求文档
    ↓
主智能体 → 计划智能体 → 生成任务计划
    ↓
对每个任务：
    ├─ 启动开发智能体（新的，独立 worktree）
    │   ↓
    │  开发完成 → 返回结果路径
    │   ↓
    ├─ 启动测试智能体（新的）
    │   ↓
    │  测试完成 → 返回结果路径
    │   ↓
    ├─ 判断测试结果
    │   ├─ 通过 → 下一个任务
    │   └─ 失败 → 通知同一个开发智能体修复
    │              ↓
    │           修复完成
    │              ↓
    │           同一个测试智能体重测
    │              ↓
    │           重复直到通过（最多3次）
    ↓
所有任务完成 → 生成项目报告
```

### 状态转换

```
pending (待处理)
  ↓
in_progress (开发中)
  ↓
testing (测试中)
  ├─ 通过 → completed (已完成)
  └─ 失败 → failed (失败) → in_progress (修复) → testing (重测)
```

## 🔧 技术实现

### 智能体配置

```yaml
计划智能体:
  模型: opus
  隔离: 无
  超时: 10分钟
  生命周期: 一次性

开发智能体:
  模型: sonnet
  隔离: worktree（独立工作空间）
  超时: 30分钟
  生命周期: 任务完成后释放
  复用: 同一任务的修复

测试智能体:
  模型: sonnet
  隔离: 无（共享环境）
  超时: 10分钟
  生命周期: 任务验收后释放
  复用: 同一任务的重测
```

### 通信协议

**主智能体 → 计划智能体：**
```json
请求: {"action": "create_plan", "requirements_path": "..."}
响应: {"status": "success", "plan_path": "...", "total_tasks": 10}
```

**主智能体 → 开发智能体：**
```json
请求: {"action": "develop", "task_id": "...", "task_title": "..."}
响应: {"status": "success", "dev_result_path": "...", "changed_files": [...]}
```

**主智能体 → 测试智能体：**
```json
请求: {"action": "test", "task_id": "...", "dev_result_path": "..."}
响应: {"status": "success", "test_result_path": "...", "test_passed": true}
```

## 💡 关键创新

### 1. 智能体生命周期管理

**问题：** 如何管理多个智能体的创建、保持、释放？

**解决方案：**
- 开发智能体：每个任务创建新的，修复时复用同一个
- 测试智能体：每个任务创建新的，重测时复用同一个
- 计划智能体：一次性使用，完成后立即释放

**优势：**
- 避免上下文污染
- 提高修复效率
- 减少资源消耗

### 2. 路径传递机制

**问题：** 如何在智能体之间传递大量信息？

**解决方案：**
- 所有结果写入文件
- 智能体之间只传递文件路径
- 需要时读取文件内容

**优势：**
- 减少 token 消耗
- 支持大文档传递
- 便于审计和追溯

### 3. 状态持久化

**问题：** 如何支持中断恢复？

**解决方案：**
- 所有状态写入 `task-status.json`
- 每次状态变更立即保存
- 包含完整的任务信息和智能体 ID

**优势：**
- 支持中断恢复
- 完整的审计追踪
- 便于进度监控

### 4. 自动化修复循环

**问题：** 如何处理测试失败？

**解决方案：**
- 测试失败时，通知同一个开发智能体
- 开发智能体修复后，同一个测试智能体重测
- 最多重试 3 次，避免无限循环

**优势：**
- 保持上下文
- 快速迭代
- 自动化程度高

## 🚀 使用示例

### 步骤 1：准备需求文档

```markdown
# 用户登录功能需求

## 功能描述
实现用户名密码登录

## 验收标准
- 正确凭证返回 token
- 错误凭证返回 401
- 响应时间 < 100ms
```

### 步骤 2：启动主智能体

```
我需要开发一个功能，需求文档在 ./doc/requirements/user-login.md
```

### 步骤 3：自动执行

主智能体会自动：
1. 启动计划智能体生成任务计划
2. 逐个执行任务（开发 → 测试 → 修复 → 重测）
3. 生成项目完成报告

## 🎓 最佳实践

### 需求文档编写

1. **功能描述清晰** - 说明做什么，为什么做
2. **验收标准明确** - 具体、可测试、可量化
3. **包含示例数据** - 输入输出示例
4. **非功能需求** - 性能、安全、可用性

### 任务拆分

1. **粒度合理** - 1-4 小时完成
2. **独立可测试** - 每个任务可独立验证
3. **依赖清晰** - 明确标注依赖关系
4. **优先级明确** - 高中低优先级

### 代码实现

1. **测试驱动** - 先写测试或同时写测试
2. **质量优先** - 代码质量比速度重要
3. **规范遵守** - 严格遵守项目规范
4. **文档完整** - 结果文档详细准确

### 测试验证

1. **全面覆盖** - 正常、异常、边界
2. **问题定位** - 不仅发现问题，还要定位原因
3. **建设性反馈** - 提供修复建议
4. **客观公正** - 基于事实，不偏袒
