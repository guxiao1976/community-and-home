# Writing Plans 技能使用模板

## 技能名称
`writing-plans`

## 功能描述
将复杂需求或设计文档分解为结构化、可执行的开发任务，包括依赖关系识别、优先级排序和工作量估算。

## 使用场景
- 架构设计完成后，需要分解为具体任务
- 复杂功能需要精细化拆分
- 多人协作需要明确任务边界
- 识别并行开发机会
- 风险评估和关键路径分析

## 输入要求

### 必需信息
- 架构设计文档或需求描述
- 项目背景和技术栈
- 团队规模和能力

### 可选信息
- 时间约束（截止日期）
- 优先级指导
- 已知风险点
- 依赖的外部系统

## 输出内容
1. 结构化任务列表（带 ID）
2. 任务依赖关系图
3. 优先级排序
4. 工作量估算
5. 风险识别

## 调用示例

### 示例 1: 用户权限管理功能拆分
```
将用户权限管理功能分解为可执行的开发任务：

## 功能需求
实现基于 RBAC 的用户权限管理系统，包括：
- 角色管理（创建、编辑、删除角色）
- 权限配置（为角色分配权限）
- 用户角色关联（为用户分配角色）
- 权限检查（API 层权限验证）

## 技术栈
- 后端：Go + go-zero + GORM + MySQL
- 前端：Vue 3 + TypeScript + Element Plus
- gRPC 服务间通信

## 团队
- 2 名后端工程师
- 1 名前端工程师

## 时间约束
2 周完成

## 任务分解要求
1. 识别可并行的任务
2. 标注前后端依赖关系
3. 估算每个任务的工时
4. 识别技术难点和风险
```

**期望输出**:
```
任务分解方案：

【阶段 1：基础设施】(P0, 阻塞后续任务)
├─ T1.1: 设计数据库表结构 (1h, Easy)
│  └─ 输出: DDL + ER 图
├─ T1.2: 定义 Proto 接口 (2h, Easy)
│  └─ 输出: permission.proto
└─ T1.3: 生成代码脚手架 (1h, Easy)
   └─ 输出: gRPC 服务框架

【阶段 2：后端核心功能】(P1, 可并行)
├─ T2.1: 角色 CRUD (4h, Easy) [依赖: T1.3]
├─ T2.2: 权限 CRUD (4h, Easy) [依赖: T1.3]
├─ T2.3: 角色权限关联 (6h, Medium) [依赖: T2.1, T2.2]
└─ T2.4: 用户角色关联 (4h, Easy) [依赖: T2.1]

【阶段 3：权限检查中间件】(P1, 阻塞前端)
└─ T3.1: gRPC 权限检查实现 (8h, Hard) [依赖: T2.3, T2.4]
   └─ 风险: 性能优化（需要缓存）

【阶段 4：前端界面】(P1, 可并行)
├─ T4.1: 角色管理页面 (6h, Medium) [依赖: T2.1, T3.1]
├─ T4.2: 权限配置页面 (8h, Hard) [依赖: T2.3, T3.1]
└─ T4.3: 用户角色分配页面 (6h, Medium) [依赖: T2.4, T3.1]

【阶段 5：测试和文档】(P2)
├─ T5.1: 单元测试 (8h, Medium) [依赖: T2.*, T3.*]
├─ T5.2: E2E 测试 (6h, Medium) [依赖: T4.*]
└─ T5.3: API 文档和使用手册 (4h, Easy) [依赖: 全部]

【并行度分析】
- 阶段 1: 串行（3 个任务）
- 阶段 2: 可并行（4 个任务，2 人可同时开发）
- 阶段 3: 串行（1 个关键任务）
- 阶段 4: 可并行（3 个任务，1 人可依次完成）
- 阶段 5: 部分并行

【关键路径】
T1.1 → T1.2 → T1.3 → T2.1 → T2.3 → T3.1 → T4.2
总工时: 1+2+1+4+6+8+8 = 30h (约 4 个工作日)

【风险识别】
1. T3.1 (权限检查) 技术难度高，可能需要额外时间优化性能
2. T4.2 (权限配置) UI 复杂，需要与产品确认交互细节
3. Proto 接口变更可能影响其他服务，需要全局评估

【资源分配建议】
- 后端工程师 A: T1.* → T2.1, T2.2 → T3.1
- 后端工程师 B: T2.3, T2.4 → T5.1
- 前端工程师: T4.1 → T4.2 → T4.3 → T5.2
```

### 示例 2: 数据库迁移任务拆分
```
将 Snowflake ID 迁移任务分解为安全的执行步骤：

## 背景
当前系统使用 MySQL 自增 ID，需要迁移到 Snowflake ID 以支持分布式部署。

## 影响范围
- 8 个微服务
- 30+ 张数据表
- 50+ gRPC 接口
- 前端 20+ 页面

## 约束
- 不能停机
- 需要保持数据一致性
- 支持回滚

## 任务分解要求
1. 分阶段迁移，降低风险
2. 每个阶段可独立验证
3. 标注回滚点
```

**期望输出**: 分阶段迁移计划，每个阶段都是可验证、可回滚的...

### 示例 3: 性能优化任务拆分
```
将 API 性能优化分解为具体的优化任务：

## 当前问题
- 用户列表接口响应时间 3-5s（目标 < 500ms）
- 高峰期 CPU 使用率 80%+
- 数据库连接池经常耗尽

## 性能分析结果
- N+1 查询问题（关联查询未优化）
- 缺少索引（phone, created_at 字段）
- 未使用缓存（热点数据重复查询）
- 返回字段过多（不必要的 JOIN）

## 优化目标
- 响应时间 < 500ms
- CPU 使用率 < 50%
- 支持 1000+ 并发

## 任务分解要求
1. 按优化效果排序（先做收益大的）
2. 标注每个优化的预期收益
3. 识别可能的副作用
```

**期望输出**: 优化任务列表，按预期收益排序...

## 最佳实践

### 1. 提供充分的上下文
✅ 好的输入：
```
- 清晰的功能需求
- 技术栈和架构约束
- 团队规模和能力
- 时间和质量要求
```

❌ 模糊的输入：
```
"把这个功能做出来"
```

### 2. 明确拆分粒度
- **粗粒度**：适合高层规划（史诗级任务）
- **细粒度**：适合执行层（< 1 天完成）
- **推荐**：1-2 天完成一个任务

### 3. 识别依赖关系
```
T2 依赖 T1: T1 必须完成后 T2 才能开始
T3 阻塞 T4, T5: T3 未完成，T4 和 T5 无法开始
```

### 4. 合理估算工时
- 考虑开发、测试、Review 时间
- 预留 20-30% 缓冲（应对未知问题）
- 区分理想时间和实际时间

### 5. 标注技术难度
- **Easy**: 重复性工作，无技术挑战
- **Medium**: 需要设计，有一定复杂度
- **Hard**: 技术难点，需要深入研究

## 与其他技能配合

### writing-plans + executing-plans
```
1. writing-plans 生成任务列表
2. executing-plans 按计划执行
3. 进度跟踪和调整
```

### writing-plans + harness-pipeline
```
1. 架构设计完成
2. writing-plans 分解任务
3. harness-pipeline 执行每个任务
4. 自动化开发流程
```

## 注意事项

1. **任务拆分粒度**
   - 太粗：难以跟踪进度，风险不可控
   - 太细：管理成本高，失去灵活性
   - 推荐：1-2 天完成

2. **依赖关系清晰**
   - 明确阻塞关系
   - 识别可并行任务
   - 优化关键路径

3. **优先级合理**
   - P0: 阻塞性任务
   - P1: 核心功能
   - P2: 增强功能
   - P3: 优化改进

4. **工时估算保守**
   - 考虑不确定因素
   - 预留缓冲时间
   - 区分理想与实际

5. **风险提前识别**
   - 技术难点
   - 外部依赖
   - 资源瓶颈

## 常见问题

### Q: 如何决定任务拆分的粒度？
A: 遵循"1-2 天完成"原则。太细管理成本高，太粗风险不可控。

### Q: 如何处理任务依赖？
A: 明确标注依赖关系，绘制依赖图，识别关键路径，优化并行度。

### Q: 工时估算总是不准怎么办？
A: 记录实际耗时，积累历史数据，提高估算准确性。预留 20-30% 缓冲。

### Q: 任务执行中发现需要调整怎么办？
A: 任务规划不是一成不变的，根据实际情况动态调整优先级和范围。
