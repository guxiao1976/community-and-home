# 上下文管理方案（Context Management）

> 状态：2026-08-16 立项实施。解决 L 级长任务单会话上下文溢出（token 上限中断开发）与执行期无进度反馈两大缺陷。
> 触发来源：task-2026-08-16-001 运维验证阶段在单会话触发上下文上限；用户提出"执行过程需每 5 分钟进度报告 + 上下文 70% 阈值干预"。

---

## 1. 问题诊断

### 1.1 owner-agent 是唯一编排中枢，但"管控环"就是上下文放大器

owner-agent.md 声明"纯编排器、上下文保持干净、只读摘要"，**实际只落地一半**：

| 阶段 | 设计声明 | 实际执行 | 主会话上下文负担 |
|------|---------|---------|:---:|
| 1-3 分析/评审/设计 | 子 Agent 隔离 | ✅ 子 Agent | 低 |
| 5 编码 | Workflow 子 Agent | ✅ 子 Agent | 中（结果摘要回主会话） |
| 4 Proto | Owner 内联 | ⚠️ 主会话 | 中 |
| 6 集成/运维验证 | Owner 内联 | ❌ 主会话全量内联 | **极高** |
| QA FAIL 闭环（TDD 证据等） | 未定义 | ❌ 主会话 | **极高** |

上次溢出发生在阶段 6 运维验证 + QA 闭环——这两个**输出密集型**阶段设计上就该是子 Agent，实际却全在主会话。

### 1.2 上下文消耗量级（单 L 级任务）

| 消耗源 | 量级 | 说明 |
|--------|------|------|
| `tasks.md` 直读 | ~27k tokens | 87KB 执行清单 |
| `design.md` 直读 | ~25k tokens | 82KB 设计文档 |
| QA 报告（4 服务） | ~10-15k | 每份 `_qa.md` 大段表格 |
| `harness-checks` JSON × 多次 | ~10k | QA 循环反复跑 |
| E2E 验证工具输出 | ~40-60k | 迁移 + 冒烟几十次 curl/DB/日志 |
| 大文件反复重读 | ~10-20k | QA 闭环/TDD 证据复现 |

**单 L 级任务主会话累积 90-130k tokens 是常态**，验证多跑几轮即爆。

### 1.3 根因（三层）

1. **设计层**：阶段 6"Owner 内联验证"设计错误——验证是输出密集型，恰是最不该在主会话的阶段。
2. **操作层**：全程无上下文监控、无预算门禁。无"我 72% 了该 compact"的可观测性。
3. **结构层**：无会话卫生协议——大文件直接进主会话、验证输出直接进主会话、无阶段级 handoff 断点。

## 2. 任务-会话分类（主会话 vs 新会话）

判据：**主会话只保留"薄上下文决策"；一切"重上下文执行"进子 Agent 或新会话。**

### 2.1 必须主会话（薄，决策型）

| 任务 | 原因 | 上下文需求 |
|------|------|:---:|
| dispatch 分级 / 路径选择 | 硬约束 #7，编排入口 | 低 |
| HITL 决策点（5 个） | 用户交互 | 低 |
| Proto 变更 + `make ci` | 硬约束 #2 全局专属 | 中 |
| go/no-go 裁决 + 置信度审查 | 只读产出摘要 | 低 |
| 知识/CHANGELOG/BACKLOG 决策 | 编排收尾 | 低 |

### 2.2 必须新会话/子 Agent（重上下文，执行型）

| 任务 | 现状 | 应改为 |
|------|------|--------|
| 运维验证（Task 6.x：迁移+E2E） | ❌ 主会话内联 | **独立子 Agent/新会话**，回传验证结果摘要 |
| QA FAIL 闭环（TDD 证据/bug 修复） | ❌ 主会话 | 独立子 Agent，回传证据文件路径 + 结论 |
| 服务实现（pipeline） | ✅ 子 Agent | 维持 |
| 分析/评审/设计 | ✅ 子 Agent | 维持 |

**关键原则**：子 Agent/新会话产出**落盘文件**（`_qa.md`/`_tdd_evidence.md`/验证报告），主会话**只读文件摘要**验收。禁止主会话自行直读大文件、内联跑验证。

## 3. 上下文预算模型（科学阈值）

核心认知：**compact 本身需要上下文空间**。窗口 95% 满时模型无法可靠"总结自己"，触发线必须远低于满。

| 区间 | 填充率 | 状态 | 动作 |
|------|:---:|------|------|
| 🟢 健康 | ≤50% | 正常 | 无 |
| 🟡 关注 | 50-70% | 提前干预 | 阶段边界强制 /compact（自然断点、信息密度低、损失最小）；60%+ 禁止开启新阶段 |
| 🔴 强制 | 70-80% | 必须处置 | 立即 /compact（无论是否断点）；compact 后仍 >55% → 停 + 写 handoff |
| ⛔ 硬停 | >80% | 禁止继续 | 不 compact（可能失败），直接写 handoff + 结束会话，新会话续 |

**为什么 70% 而非 85%**：① compact 产摘要需要空间，85% 时可能失败；② 模型推理质量随填充率下降；③ 70% 时的信息损失可由"先落盘再 compact"抵消。

**为什么阶段边界 compact**：边界处已验收产出已落盘（`summary.md`/`_qa.md`），compact 丢的是"过程对话"而非"成果"。

## 4. 监控机制

**现实约束**：Claude Code 不向 shell hook 暴露"模型上下文填充率"API，"每 5 分钟 hook 读 %"无法纯机械实现。三层方案：

### 4.1 进度心跳（每 5 分钟，本期落地）

Monitor 工具读 `$CLAUDE_JOB_DIR/tmp/progress.txt` 单行状态文件，每 300s 发一条带时间戳的通知：

```bash
while true; do printf '[%s] %s\n' "$(date '+%H:%M:%S')" "$(cat $CLAUDE_JOB_DIR/tmp/progress.txt 2>/dev/null || echo '无进度标记')"; sleep 300; done
```

执行 Agent 在每个步骤边界 `echo "当前: <做什么>" > $CLAUDE_JOB_DIR/tmp/progress.txt`。用户随时可看"在跑 + 在哪一步"，不会误判卡死。

### 4.2 确定性检查点（模型自我执行，主方案）

模型按 `context-budget` skill 在固定 gate 跑 `/context` 并按预算表决策：
- 每个阶段开始前 + 结束后（L 级 12 个检查点）
- 任何新文件 >50KB 读取前（先问：能不能交子 Agent 读？）
- QA 循环每轮结束（QA 是输出大户）

### 4.3 Statusline context 组件（可选增强）

用 statusline-setup 在状态栏显示实时填充率。**注意**：会覆盖 shell prompt，与自定义 `.bashrc` prompt 冲突，默认不启用；如需启用由用户拍板。

## 5. 会话交接协议（新会话可靠续的前提）

新会话能接手的唯一前提：**成果已落盘 + 交接文件指向明确。**

1. **L 级任务按阶段拆会话**：`设计会话 → 实现会话(N×pipeline) → 验证会话 → 收尾会话`
2. **交接文件标准**（复用变更目录 `summary.md`），固定小节：
   - `## 当前阶段`：阶段 + 已验收产出文件列表
   - `## 上下文快照`：已完成决策摘要 + 剩余任务 + **大文件路径而非内容**
3. **会话卫生硬规则**：
   - 主会话禁止直读 >50KB 文件（`tasks.md`/`design.md` → 只读相关小节或交子 Agent）
   - 主会话禁止内联跑验证（Task 6.x → 派子 Agent，回传摘要）
   - 每阶段结束写 `summary.md` 小节 = 后续任何会话的唯一入口
4. **resume**：`claude -r <session-id>`（CLI 已验证支持）。

## 7. 验证标准

- 心跳：Monitor 每 5 分钟送达带时间戳 + 当前活动的通知（已实测 ✅ 2026-08-16）
- 门禁：L 级任务任一阶段执行前有 `/context` 检查记录；>70% 时有 compact 动作；>80% 时有 handoff 文件
- 会话卫生：主会话不再直读 >50KB 文件、不再内联跑 Task 6.x 验证
