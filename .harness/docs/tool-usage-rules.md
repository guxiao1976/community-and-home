# Agent 工具使用规则

> 本文档定义 Agent 在不同场景下应该使用哪些工具，以及应该避免什么操作。
> 
> **目标**：提升 Agent 决策准确性，避免不必要的工具调用。

## 📋 核心原则

1. **上下文优先**：根据用户消息类型选择工具，而非固定模式
2. **最小操作**：只执行完成任务所需的最少工具调用
3. **反馈即行动**：工具输出应指导下一步操作

---

## 🎯 场景 → 工具映射

### 场景1: 用户发送日志/错误信息

**识别特征**：
- 消息包含日志格式（`[timestamp]`, `ERROR`, `WARN`）
- 包含错误码（`code: 50001`）
- 包含堆栈跟踪
- 明确是问题排查

**应该做**：
```
1. 直接分析日志内容
2. 识别错误类型和原因
3. 给出诊断和解决方案
4. 如果需要查看代码，使用 Read
```

**不应该做**：
```
❌ 不扫描任务 (harness-tasks.sh scan)
❌ 不运行 QA 检查
❌ 不检查知识图谱新鲜度
❌ 不提交代码
```

**示例**：
```
用户: [DEBUG] API Response: {code: 50001, message: '该手机号未注册'}
Agent: [分析日志] → 错误原因是用户未注册 → 给出解决方案
```

---

### 场景2: 代码开发完成，要求提交

**识别特征**：
- 用户说"提交代码"、"commit"、"完成开发"
- 代码修改已完成
- 需要记录变更

**应该做**：
```
1. 检查修改的文件 (git status)
2. 暂存文件 (git add)
3. 提交 (git commit)
4. 如果是重要功能，询问是否需要完整的工作流
```

**不应该做**：
```
❌ 不立即扫描任务（提交后再扫描）
❌ 不读取无关文件
```

---

### 场景3: 完成一个完整需求/功能

**识别特征**：
- 用户说"完成XXX功能的记录和验证"
- 功能开发已完成
- 需要完整的后续流程

**应该做（按顺序）**：
```
1. 更新变更索引 (.harness/changes/INDEX.md)
2. 提交所有修改 (git add + commit)
3. 运行 QA 检查 (harness-tasks.sh scan)
4. 同步知识图谱 (graph-sync.sh)
5. 最终扫描确认无遗漏
6. 生成总结报告
```

**不应该做**：
```
❌ 不跳过任何步骤
❌ 不打乱顺序
❌ 不重复执行相同检查
```

**使用工作流脚本**（优化后）：
```bash
bash .harness/scripts/complete-feature.sh "功能名称" "commit消息"
```

---

### 场景4: 启动服务/系统

**识别特征**：
- 用户说"启动前端"、"启动微服务"、"start"
- 需要运行服务

**应该做**：
```
1. 检查服务状态 (避免重复启动)
2. 检查依赖（如数据库、Redis）
3. 启动服务
4. 验证端口监听
5. 报告启动结果
```

**不应该做**：
```
❌ 不扫描任务
❌ 不运行 QA 检查
❌ 不重复启动已运行的服务
```

---

### 场景5: 排查系统问题

**识别特征**：
- 用户说"为什么XXX不工作"、"排查XXX问题"
- 功能异常

**应该做**：
```
1. 检查服务状态
2. 查看相关日志
3. 检查配置文件
4. 分析问题原因
5. 给出解决方案
```

**不应该做**：
```
❌ 不扫描任务（除非问题是"有哪些待办"）
❌ 不修改代码（除非明确要求修复）
```

---

### 场景6: 运行测试/QA检查

**识别特征**：
- 用户说"运行测试"、"QA检查"、"质量验证"
- 代码修改后需要验证

**应该做**：
```
1. 运行相关测试
2. 运行 QA 检查
3. 报告结果
4. 如果失败，给出修复建议
```

**不应该做**：
```
❌ 不立即修复（除非用户要求）
❌ 不扫描任务（QA工具已包含）
```

---

### 场景7: 查询状态/信息

**识别特征**：
- 用户问"有哪些任务"、"服务状态"、"最近的提交"
- 纯查询，无修改

**应该做**：
```
1. 使用相应的查询工具
2. 格式化输出结果
```

**不应该做**：
```
❌ 不执行修改操作
❌ 不运行检查（除非明确要求）
```

---

## 🔄 工作流阶段定义

### 阶段1: 开发中
- 专注于代码实现
- 频繁测试
- 不需要完整检查

### 阶段2: 开发完成
- 运行完整测试
- 提交代码
- 更新文档

### 阶段3: 功能完成
- 执行完整工作流
- 更新变更索引
- 同步知识图谱
- 最终验证

## 🚫 反面案例

### 案例1: 收到日志时扫描任务 ❌

```
用户: [DEBUG] {code: 50001, message: '用户未注册'}
Agent: bash .harness/scripts/harness-tasks.sh scan  ← 错误！
```

**为什么错**：用户发送日志是为了排查问题，不是要检查待办任务

**正确做法**：
```
Agent: 分析日志 → 错误原因是用户未注册 → 建议注册或检查数据库
```

---

### 案例2: 简单查询时运行完整检查 ❌

```
用户: 微服务都起来了吗？
Agent: bash .harness/scripts/run-all-checks.sh  ← 错误！
```

**为什么错**：用户只是查询状态，不需要运行测试

**正确做法**：
```
Agent: bash scripts/status.sh → 报告服务状态
```

## 📊 决策流程图

```
用户消息
  ↓
识别消息类型
  ↓
┌─────────────────────────────────────┐
│ 是日志/错误? → 是 → 分析日志       │
│      ↓ 否                           │
│ 是提交请求? → 是 → git操作         │
│      ↓ 否                           │
│ 是功能完成? → 是 → 完整工作流      │
│      ↓ 否                           │
│ 是启动服务? → 是 → 启动服务        │
│      ↓ 否                           │
│ 是查询状态? → 是 → 查询工具        │
│      ↓ 否                           │
│ 根据具体内容决策                    │
└─────────────────────────────────────┘
```

---

## 🎓 记忆要点

1. **日志 = 立即分析**，不扫描任务
2. **完成需求 = 完整工作流**，不遗漏步骤
3. **查询 = 查询工具**，不执行操作
4. **疑问时 = 问用户**，不猜测意图
