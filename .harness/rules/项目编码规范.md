# 项目编码规范

> 稳定约束 · 适用于所有服务和子 Claude 实例 · 最后更新 2026-06-12

---

## 1. 服务间通信

**所有服务间通信必须通过 gRPC 接口**，接口定义在 `api-proto/` 中。

- ❌ 禁止直接访问其他服务的数据库
- ❌ 禁止服务间 HTTP 调用
- ✅ 调用其他服务 → gRPC（etcd 服务发现）

相关记忆：[[grpc-only-comms]]

## 2. Proto 变更权限

**Proto 变更必须在全局 Claude 实例中执行**。子 Claude 实例禁止修改 `api-proto/`。如需修改 proto，子实例应告知用户切换到全局 Claude。

详见 `.harness/rules/Proto管理规范.md`

## 3. common/ 变更影响

**修改 `common/` 会影响所有依赖服务**。涉及 common 的变更需要全局 Claude 评估影响范围。

## 4. go.work 联调规则

本地开发通过 `go.work` 解析模块依赖，修改 common 或 api-proto 后各服务立即可见新代码，无需远程发布。

## 5. Snowflake ID 序列化规范

> JavaScript 安全整数兼容

Snowflake 生成 19 位 ID，超过 JS `Number.MAX_SAFE_INTEGER`（~16 位），JSON 数字解析时精度丢失。

| 层 | 要求 |
|----|------|
| **Proto** | 所有 `int64` ID 字段必须添加 `[jstype = JS_STRING]`，确保 protojson 序列化时以字符串输出 |
| **Go REST API** | 所有 `int64` ID 字段必须使用 `json:"...,string"` 标签 |
| **前端 TypeScript** | 所有 ID 字段类型必须为 `string`，axios 使用 `lossless-json` 解析器 |

> 注意：`repeated int64` 字段也需要加 `[jstype = JS_STRING]`

相关记忆：[[proto-jstype]]

### 5.1 时间字段命名全链路一致性

各层时间字段名必须一致。Proto 定义是契约，上下游跟随。

```
DB column      →  created_at / updated_at / deleted_at    （MySQL）
Proto field    →  created_at / updated_at / deleted_at    （api-proto）
Go json tag    →  created_at / updated_at / deleted_at    （types.go）
TS interface   →  created_at / updated_at / deleted_at    （types/*.ts）
Vue 模板       →  row.created_at   ❌ 不是 row.createdAt
```

QA 自动检查：`bash .harness/skills/qa/scripts/check-api-field-align.sh`

相关记忆：[[snake-camel-field-mismatch]]

### 5.2 雪花 ID 列宽

Snowflake 生成 19 位数字，前端 `el-table-column` 的 ID 列宽统一为 **200px**，禁止小于此值。

```
<el-table-column prop="id" label="ID" width="200" />
```

## 9. REST API 响应格式

### 9.1 单层包装原则

**Logic 返回纯业务数据，Handler 统一用 `response.Success()` 包一层。禁止双层嵌套。**

```
正确：Handler ──response.Success(w, data)──→ {code:0, msg:"success", data: <业务数据>}
错误：Handler ──response.Success(w, resp)──→ {code:0, msg:"success", data: {code:0, data:...}}
                                                    ↑ resp 自己就带 BaseResponse，造成双层
```

| 层 | 职责 | 禁止 |
|----|------|------|
| **Logic** | 返回纯业务数据（struct/pointer），不嵌 `BaseResponse` | 返回 goctl 自动生成的 `*Response` 类型 |
| **Handler** | 调用 Logic → 用 `response.Success(w, data)` 包一层 → 输出 JSON | 在 Handler 层再次包装已经是 Response 类型的值 |

### 9.2 goctl 生成类型的处理

goctl 生成的 Request 类型可以使用，但 goctl 生成的 Response 类型（嵌 `BaseResponse`）**不应作为 Logic 返回值**。正确做法：

```go
// Logic 返回业务数据
func (l *CreateModelLogic) CreateModel(req *types.CreateModelRequest) (*model.AmModelConfig, error) {
    // ... 创建模型 ...
    return &createdModel, nil
}

// Handler 包装
func CreateModelHandler(svcCtx *svc.ServiceContext) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        // ...
        l := model.NewCreateModelLogic(r.Context(), svcCtx)
        data, err := l.CreateModel(&req)
        if err != nil {
            response.Error(w, err)
        } else {
            response.Success(w, data)  // ← 只包一层
        }
    }
}
```

### 9.3 前端响应解析

axios 拦截器从 `response.data` 提取 `data` 字段再返回。由于后端遵循单层包装，前端代码中 `res` 直接就是业务数据：

```typescript
// 正确：后端单层包装，res 就是业务数据
const res = await getModelConfigs({...});
tableData.value = res.models;   // ✅ res = {models: [...], total: N}

// 错误：如果后端双层嵌套，需要 res.data.models
tableData.value = (res as any)?.data?.models;  // ❌ 不该出现
```

### 9.4 API 代理路径对齐

Vite proxy 配置中的 `/api/v1` 路径必须与后端 API handler 的 `rest.WithPrefix("/api/v1")` 一致。新服务注册路由时，优先使用 `/api/v1` 前缀（apikey/template/cost 等已统一）。

## 10. Vue 模板中避免嵌套插值

Vue 模板编译器会将 `{{` 视为插值表达式起始。在 `{{ }}` 内部不能出现 `{{` 字符串（即使作为字面量引号内），否则报 `Unterminated string constant`。

```vue
<!-- ❌ 错误：'{{' 被解析为嵌套插值 -->
<el-tag>{{ '{{' + v + '}}' }}</el-tag>

<!-- ✅ 正确：拆开花括号 -->
<el-tag>{{ '{' + '{' + v + '}' + '}' }}</el-tag>
```

## 12. 编辑回显数据完整性

> **新增或修改任何表单字段时，必须验证"创建→存储→读取→编辑回显"全链路数据不丢失。**

### 12.1 核心原则

编辑页面打开时，**所有表单字段（包括下拉框、开关、输入框）的值必须与列表行数据一致**。用户不应该看到"编辑页面的下拉框选项和列表行不一样"。

### 12.2 检查清单

新增或修改表单字段时，必须逐层确认：

| # | 层 | 检查项 |
|---|----|--------|
| 1 | **Proto** | 字段已添加到对应的 Request / Response 消息 |
| 2 | **后端 types.go** | 字段已添加到 `CreateXxxRequest` / `UpdateXxxRequest` / `XxxInfo` |
| 3 | **后端 Create Logic** | 字段已传递给 RPC 并存入数据库 |
| 4 | **后端 Update Logic** | 字段已传递给 RPC 并更新数据库 |
| 5 | **后端 Get/List Logic** | 字段已从 RPC 响应映射到 API 响应 |
| 6 | **前端 TS 类型** | 字段已添加到对应的 interface |
| 7 | **前端 API 函数** | `createXxx()` / `updateXxx()` 参数类型包含该字段 |
| 8 | **前端 fetchData** | 编辑回显时 `Object.assign` 包含该字段 |

### 12.3 常见反模式

```typescript
// ❌ 表单有字段，但 API 类型没加 —— 字段被 TS 编译时丢弃
const baseData = { ..., model_type: formData.model_type };
await createModelConfig(baseData);  // createModelConfig 签名没有 model_type

// ❌ 后端存了，但 Get 接口没返回 —— 编辑页永远显示默认值
Object.assign(formData, { model_type: model.model_type || 'cloud' });  // model.model_type 是 undefined

// ❌ Proto 加了字段，但 RPC Logic 没用新字段名
ModelType: in.Type,  // 应该用 in.ModelType（新字段），in.Type 是旧字段存了错误的值
```

### 12.4 正确示例

```typescript
// ✅ 前端：API 类型、baseData、回显映射全部对齐
// aimodel.ts — 接口类型包含 model_type
export interface ModelConfig {
  model_type?: string;  // ← 新增字段
}

// ModelForm.vue — 创建时传递
const baseData = { ..., model_type: formData.model_type };
await createModelConfig(baseData);

// ModelForm.vue — 编辑时回显
Object.assign(formData, { model_type: model.model_type || 'cloud' });
```

### 12.5 典型事故

`model_type`（部署方式：cloud/local）仅在表单中有下拉框，但 Proto 的 `CreateModelConfigReq` 没有对应字段。前端通过 `...baseData` 展开发送了该字段，由于 TS 类型不含此字段且后端 `CreateModelRequest` 也没有，**数据在 HTTP 层被静默丢弃**。数据库中 `model_type` 列存储的是另一个字段 `type` 的值（"chat"），而非用户选择的 "cloud"/"local"。编辑时回显永远是默认值 "cloud"。

> 教训：**加一个表单字段 = 8 层都要加。少一层就是数据丢失。**
