# Proposal: 测试流水线工作记录模块

## 为什么做

流水线已经初步打造完成，需要在实践中验证其效果并发现改进点。通过开发一个完整的前后端功能模块（工作事项维护 + 工作内容记录），可以：

1. **验证流水线完整性**：测试从需求分析 → 架构设计 → 代码实现 → 测试验证的全流程
2. **发现流程瓶颈**：记录开发过程中的阻塞点、工具使用问题、协作痛点
3. **积累改进数据**：通过工作记录收集时间分布、问题类型等数据，为流水线优化提供依据
4. **建立基准线**：为后续流水线改进提供对比基准（开发效率、代码质量、测试覆盖率）

该模块本身也有实用价值：用于记录 AI 团队日常工作内容，统计各类事项的工作量分布。

## 做什么

在 PC 管理后台新增一级菜单"AI-Coding自我提升"，包含两个页面：

### 页面 1: 工作事项维护
- 单列表展示所有工作事项
- 支持 CRUD 操作（新增、编辑、删除、查询）
- 字段：工作事项名称、排序号、状态（启用/禁用）
- 软删除支持

### 页面 2: 工作内容记录
- 四列展示：工作事项（下拉选择）、工作日期、工作内容描述、工作时长（小时）
- 查询条件：日期范围筛选（开始日期 - 结束日期）
- 工作事项下拉列表动态加载页面 1 的启用项
- 支持 CRUD 操作

### 数据隔离
- 数据库表名使用 `pipeline_test_` 前缀，与实际项目数据区分
- API 路径使用 `/api/masterdata/pipeline-test/` 前缀
- 前端路由路径独立命名空间

| 服务/组件 | 变更类型 | 说明 |
|---------|:-------:|------|
| **master-data-service** | 新增 API | 8 个 REST 端点（工作事项 4 个 + 工作记录 4 个） |
| **master-data-service** | 数据库 | 2 张表：`pipeline_test_work_items`, `pipeline_test_work_records` |

| **web/pc** | API 层 | 8 个 TypeScript API 函数 |
| **web/pc** | 组件 | 2 个列表页面 + 2 个表单对话框 |

**不影响**：
- 其他微服务（独立模块，无服务间调用）
- 现有 master-data-service 功能（隔离的表和路由）
- 生产数据（测试数据独立前缀）

## 技术决策

### 1. 服务归属：master-data-service
**理由**：
- 主数据服务定位是"基础数据管理中心"
- 工作事项和工作记录属于元数据性质
- 该服务已有成熟的 CRUD 模式和审批流程可参考
- 避免为测试模块创建独立微服务

### 2. 不使用审批流程
**理由**：
- 测试模块数据，无需严格审批
- 简化开发流程，聚焦流水线验证
- 保留标准 CRUD 字段（created_by, updated_time 等）

### 3. 不新增 RPC 接口
**理由**：
- 仅用于管理后台展示，无其他服务消费需求
- 减少 Proto 变更，降低变更复杂度
- 未来如需 RPC 可扩展

### 4. 工作时长使用小数（小时）
**理由**：
- 便于统计（直接求和）
- 支持灵活粒度（0.5h = 30 分钟）
- 前端输入验证：正数，最多 2 位小数

### 5. 日期查询支持范围筛选
**理由**：
- 周报/月报场景需要范围查询
- 前端提供快捷选项（今天、本周、本月、自定义）

## 风险评估

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|:-----:|:----:|---------|
| 表前缀冲突 | 低 | 中 | 启动前检查 `pipeline_test_` 表是否已存在 |
| 端口冲突 | 低 | 低 | master-data-service 端口已分配（8889/8087） |
| 知识图谱同步延迟 | 中 | 低 | 开发完成后执行 `graph-sync.sh` |
| 前端路由命名冲突 | 低 | 低 | 使用独立命名空间 `/pipeline-test` |
| 工作时长输入错误 | 中 | 低 | 前端表单验证 + 后端参数校验 |

## 验收标准

### 功能验收
1. ✅ 工作事项：可新增、编辑、删除、查询，支持启用/禁用状态切换
2. ✅ 工作记录：可新增、编辑、删除、查询，工作事项下拉列表正确加载
3. ✅ 日期筛选：可按日期范围查询工作记录，快捷选项正常工作
4. ✅ 数据完整性：编辑页面所有字段正确回显（参考 [[edit-form-data-integrity]]）
5. ✅ 软删除：删除的工作事项不在下拉列表显示，但关联记录仍可查看

### 技术验收
1. ✅ 所有 API 响应单层包装（参考 [[api-response-single-wrap]]）
2. ✅ Snowflake ID 字段 JSON 序列化为字符串（参考 [[proto-jstype]]）
3. ✅ 提交前 `harness-checks.sh --service master-data-service` 全部 PASS
4. ✅ 前端 TypeScript 类型无 any，通过 `npm run build`
5. ✅ 数据库 migration 文件已执行，表结构正确

### 流水线评估验收
1. ✅ 分析日志完整记录：需求分析、架构设计、开发、测试各阶段时间和问题
2. ✅ 产出评估报告：识别流水线待改进点（至少 3 个）
3. ✅ 提出优化建议：每个改进点给出具体行动方案
