### 🔴 发现 #1：Memory 全正文搜索导致严重假阳性

**根因**: `harness-pipeline.js` Generator prompt 第 39 行规定：
```
匹配规则：关键词命中 YAML frontmatter 的 triggers 列表 OR 文件正文包含关键词
```

`phone-encryption.md` 正文中写到 "go-zero sqlx（非 GORM）"，这使得任何涉及 go-zero 或 sqlx 的任务都会误匹配手机号加密记忆。同样，`verify-api-before-calling.md` 的 trigger "API" 会匹配所有 API 相关任务。

**影响**: Generator 会在不相关的代码位置添加 `// SEE: [[phone-encryption]]` 注释，降低注释信噪比。

**修复建议**: 
- 记忆搜索应优先匹配 frontmatter `triggers`，正文匹配降权
- 利用新增的 `type` 字段过滤：分页任务属于 `guideline` 类型，应过滤掉不相关的 `pitfall`
- `triggers` 中不应放 "API" 这种通配词

### 🟡 发现 #2：5/8 服务零测试覆盖，但仅 WARN 不阻塞

| 服务 | 有测试的包 | 无测试的包 | 状态 |
|------|:---:|:---:|:---:|
| auth-service | 1 | 12 | ⚠️ 仅1包有测试 |
| user-service | 2 | 15 | ⚠️ 仅2包有测试 |
| community-hub-service | 0 | 19 | 🔴 零测试 |
| file-service | 0 | 15 | 🔴 零测试 |
| master-data-service | 0 | 36 | 🔴 零测试 |
| monitoring-service | 0 | 7 | 🔴 零测试 |
| permission-service | 0 | 13 | 🔴 零测试 |
| moderation-service | 7 | 23 | ⚠️ |

**根因**: `harness-checks.sh` 将 `go test` 0/0 检测设为 WARN 而非 FAIL。文章 Dry Run 经验表明：CI 门禁只检查状态码而忽略测试用例数为 0 的异常是常见缺陷。

**当前设计是否合理**: 合理。全面强制测试会阻塞初始开发阶段。但 Pipeline 应区分"新增代码"和"已有代码"——新增代码的 0 测试应为 FAIL。

## 阶段 3: Reviewer（9 维度审查）

### 🟡 发现 #3：`_qa.md` / `_review.md` 产出无生命周期管理

- 全项目仅 2 个 `_review.md`（ai-model-service, moderation-service），无 `_qa.md`
- 这些文件是 Pipeline 的临时产物，但没有 archive 策略
- Reviewer 启动时读取 `_qa.md`，但如果文件是旧的（上一轮 Pipeline 遗留），会产生错误判断

**修复建议**: Pipeline 结束后应归档 `_qa.md` 和 `_review.md` 到 `changes/` 目录。

## 全局扫描发现

### 🟡 发现 #4：monitoring-service 缺失 docs/design.md

CLAUDE.md 要求所有服务标配 `docs/design.md`，但 monitoring-service 缺失。Generator 在此服务上会失败。

### 🟡 发现 #5：Pipeline prompt 未使用新增的 `type` 字段

我刚才在所有记忆文件中增加了 `type` (pitfall/guideline/process/decision/model)，但 `harness-pipeline.js` 的 Generator/Reviewer prompt 没有引用这个字段进行精确匹配。

### 🟡 发现 #6：magic number 检查在 auth-service 发现了遗留硬编码

`smssendlogic.go:41` 使用 `990429` magic number，应替换为 `common/pkg/errx` 中的命名常量。
